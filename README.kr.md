# Salix Consensus - Leaderless Byzantine Consensus with Majority Quorums and Worst-Case Constant Rounds

## 1. 개요

Salix는 동기 통신과 암호학적 디지털 서명을 이용하여, 전체 노드 중 과반 미만의 비잔틴 노드와 비잔틴 클라이언트가 존재하는 환경에서 합의를 수행하는 Byzantine Consensus Protocol이다.

전체 노드 수를 $n=2f+1$로 정의하며, 최대 $f$개의 비잔틴 노드를 허용한다.

프로토콜은 다음 네 페이즈로 구성된다.

$$
\boxed{
\text{Propose}
\rightarrow
\text{Prepare}
\rightarrow
\text{Merge}
\rightarrow
\text{Commit}
}
$$

New MBQ의 주요 특징은 다음과 같다.

- $n=2f+1$ 환경에서 $f+1$개의 노드 서명을 이용한다.
- 요청 전파와 커밋 서명 수집을 별도의 페이즈로 분리한다.
- Merge에서 유효한 요청에 대한 Commit 서명을 수집한다.
- Commit에서 유효한 Commit Certificate를 검증하고 반영한다.
- 고정된 4개 페이즈를 사용한다.
- 별도의 Fail Recovery는 지원하지 않는다.

## 2. 시스템 모델 및 가정

### 2.1. 노드 구성

전체 노드 수는 다음과 같다.

$$
n=2f+1
$$

- 정직한 노드: 최소 $f+1$개
- 비잔틴 노드: 최대 $f$개

비잔틴 노드는 다음 행위를 할 수 있다.

- Equivocation
- Silent 및 Partial Silent
- Collusion
- Crash
- 임의의 잘못된 메시지 전송

### 2.2. 클라이언트

클라이언트 역시 비잔틴일 수 있다.

비잔틴 클라이언트는 다음 행위를 할 수 있다.

- 사칭 시도
- 거짓 요청
- Replay
- Concurrent Request
- 임의의 요청 식별자 생성

클라이언트의 신원과 요청 인증은 암호학적 서명을 통해 검증한다.

### 2.3. 암호학적 가정

1. 노드와 클라이언트는 서로의 공개키를 알고 있으며 서명을 검증할 수 있다.
2. 디지털 서명은 위조할 수 없다.
3. 해시 함수는 충돌 저항성을 만족한다.
4. 정직한 노드는 자신이 생성한 서명을 임의로 위조하거나 변조하지 않는다.
5. 모든 노드는 클라이언트의 요청 서명을 이미 알고 있으며, 해당 서명을 검증할 수 있다.

클라이언트 서명은 모든 노드가 이미 알고 있다는 가정에 따라 Propose 메시지에 별도로 포함하지 않는다.

### 2.4. 네트워크

네트워크는 동기식이다.

$\Delta$를 정직한 노드 간 메시지 전달 지연의 상한으로 정의한다.

정직한 노드가 전송한 메시지는 정해진 시간 내에 다른 정직한 노드에게 전달된다.

### 2.5. Fail Recovery

New MBQ는 프로토콜 자체의 Fail Recovery를 지원하지 않는다.

합의 도중 발생한 노드 장애에 대한 복구 및 재개는 프로토콜의 보장 범위에 포함하지 않는다.

이는 구현체단에서 구현할 수 있다.

## 3. 요청 및 합의 식별

### 3.1. 요청 구성

클라이언트는 합의 요청을 생성할 때 다음 정보를 제공한다.

```text
Request {
    proposeId
    requestId
    clientRequest
    clientSignature
}
```

`clientSignature`는 모든 노드가 검증할 수 있도록 이미 공유되어 있다는 전제를 사용한다. 따라서 실제 Propose 메시지에는 별도로 포함하지 않는다.

### 3.2. Propose ID

합의 인스턴스의 식별자인 `proposeId`는 다음과 같이 정의한다.

$$
proposeId =
H(
clientSignature
\parallel
clientRequest
\parallel
requestId
)
$$

동일한 요청 정보에 대해서는 동일한 `proposeId`가 생성된다.

서로 다른 요청 내용이 동일한 `proposeId`를 갖는 상황은 해시 충돌 저항성에 의해 배제한다.

따라서 하나의 합의 인스턴스 ID에 서로 다른 요청 내용을 연결할 수 없다.

### 3.3. Request ID

`requestId`는 요청의 고유성과 멱등성을 관리하는 식별자다.

주요 규칙은 다음과 같다.

- 동일한 논리적 요청을 재전송하는 경우 동일한 `requestId`를 사용한다.
- 동일한 요청 내용이라도 새로운 작업이라면 새로운 `requestId`를 사용할 수 있다.
- 요청 내용이 다르면 동일한 `requestId`를 사용하더라도 별개의 요청으로 취급한다.
- `requestId`는 반드시 순차적이거나 전역적으로 유일할 필요가 없다.

예시:

| 요청 | Request ID | 처리 |
|---|---:|---|
| PUT x = 10 | 1 | 신규 작업 |
| PUT x = 20 | 2 | 신규 작업 |
| PUT x = 10 | 3 | 별개의 신규 작업 |
| PUT x = 10 | 1 | 기존 작업의 재전송 |

동일한 논리적 요청이 여러 번 커밋되더라도 SM에는 한 번만 반영되어야 한다.

중복 반영 여부는 클라이언트의 신원, `requestId`, 요청 내용을 기준으로 판단한다.

## 4. Commit Certificate

Commit Certificate(CC)는 특정 합의 인스턴스에 대한 노드들의 서명 집합이다.

유효한 CC는 다음 조건을 만족해야 한다.

1. 서로 다른 노드의 서명을 최소 $f+1$개 포함한다.
2. 모든 서명은 유효해야 한다.
3. 모든 서명은 동일한 `proposeId`에 대응해야 한다.
4. 모든 서명은 동일한 세부 요청 데이터에 대응해야 한다.

$$
|CC|\geq f+1
$$

서명 자체가 서로 다르더라도, 동일한 `proposeId`와 동일한 세부 데이터를 대상으로 하는 $f+1$개 이상의 유효한 서명 집합은 동일한 합의 결과에 대한 CC로 취급한다.

하나의 합의 인스턴스에서 생성된 CC는 해당 인스턴스에만 유효하다.

## 5. 프로토콜 페이즈

### 5.1. Propose

**목적: 합의의 시작.**

클라이언트는 자신이 생성한 요청을 노드에게 전달한다.

```text
Propose(
    proposeId,
    requestId,
    clientRequest
) -> ()
```

클라이언트로부터 요청을 수신한 노드는 해당 요청의 전파를 시작한다.

Propose는 합의 시작을 알리는 단계이며, 이 단계 자체에서 Commit 서명을 수집하지 않는다.

### 5.2. Prepare

**목적: 요청의 전파 및 상태 교환.**

노드는 Propose를 수신하면 해당 요청을 다른 노드들에게 전달한다.

```text
Prepare(
    proposeId,
    requestId,
    clientRequest
) -> ()
```

Prepare의 주요 목적은 비잔틴 노드가 Propose를 일부 노드에게만 전달하거나 특정 노드에게 침묵하는 상황을 보완하는 것이다.

정직한 노드는 수신한 Propose 요청을 다른 노드들에게 전파한다. Prepare단에서 요청 받은 정보는 전파하지 않는다.

동기 네트워크 가정 아래, 하나 이상의 정직한 노드가 요청을 수신하고 전파를 수행하면 모든 정직한 노드가 해당 요청을 수신할 수 있다.

Prepare는 별도의 투표나 커밋 결정 단계가 아니다.

### 5.3. Merge

**목적: 요청 유효성 검증 및 Commit 서명 수집.**

각 노드는 자신의 기존 상태와 무관하게 다른 노드들에게 해당 합의 인스턴스에 대한 유효성 및 서명을 요청한다.

```text
Merge(
    proposeId
) -> (
    isValid,
    commitSignature
)
```

요청을 받은 노드는 다음을 검증한다.

- `proposeId`의 해시 검증
- 클라이언트 서명 검증
- 요청의 형식 및 구현체별 추가 유효성 규칙
- 이미 처리된 요청인지 여부 등 구현체에서 요구하는 조건

유효성 검증 결과는 다음과 같다.

```text
isValid = 1
```

요청이 유효하면 해당 노드는 `proposeId`와 요청 데이터에 결합된 Commit 서명을 생성하여 응답한다.

유효하지 않은 요청에는 Commit 서명을 제공하지 않는다.

구현체별 추가 Valid 규칙은 동일한 검증 입력에 대해 모든 정직 노드가 동일한 결과를 내야 한다.

Merge가 종료되면 각 노드는 수집한 서명을 바탕으로 CC를 구성한다.

### 5.4. Commit

**목적: 인증서 검증 및 최종 반영.**

```text
Commit(
    proposeId,
    isCommitted,
    commitCert
) -> ()
```

노드는 다음 조건을 만족하는 경우 합의를 성공으로 처리한다.

1. `isCommitted = 1`
2. Commit Certificate가 유효하다.
3. CC에 동일한 `proposeId` 및 세부 데이터에 대한 $f+1$개 이상의 서로 다른 노드 서명이 포함되어 있다.

유효한 CC를 수신한 정직 노드는 자신의 기존 주장이나 이전 상태와 관계없이 해당 CC를 인정하고 요청을 반영한다.

Commit 페이즈에서 수신한 유효한 CC만 최종 커밋 인증서로 인정한다.

유효한 CC를 확보하지 못하면 해당 합의 인스턴스는 실패로 간주한다.

Commit 페이즈에서 CC를 다른 노드들에게 전파하여 정직 노드들이 동일한 인증서를 확인할 수 있도록 한다.

## 6. Phase Stability

각 노드는 현재 페이즈에서 자신을 포함한 서로 다른 $f+1$개 노드의 유효한 응답을 확보하면 대기 타이머 $s_k$를 시작한다.

타이머가 만료되면 해당 페이즈를 종료하고 다음 페이즈로 전환한다.

### 6.1. 페이즈 전환 투표

- 자신의 현재 페이즈 연산이 완료되면 자기 자신을 페이즈 전환 투표에 포함한다.
- 서로 다른 노드의 유효한 응답만 투표수로 인정한다.
- 유효하지 않은 서명이 포함된 응답은 투표수에 포함하지 않는다.
- 자신을 포함한 $f+1$개 노드의 유효한 응답을 확보한 뒤 타이머를 시작한다.

### 6.2. 타이머 조건

$s_k$는 다음 조건을 만족해야 한다.

$$
s_k\geq \Delta+B_k
$$

- $\Delta$: 메시지 전달 지연 상한
- $B_k$: 해당 페이즈 시작 시점의 정직 노드 간 진입 편차 상한
- $s_k$: 해당 페이즈의 대기 시간

### 6.3. 페이즈 종료 이후의 요청

이미 종료된 페이즈에 도착한 메시지는 거부한다.

이는 이전 페이즈의 메시지를 이용한 지연 삽입 공격을 방지하기 위함이다.

### 6.4. 미래 페이즈 요청

아직 시작하지 않은 미래 페이즈의 요청을 수신하면 다음 응답을 반환한다.

```text
Try again
```

이 응답은 어떠한 합의 주장이나 투표도 의미하지 않는다.

발신자는 해당 요청을 재시도 대상으로 취급한다.

재시도에는 백오프와 횟수 상한을 적용한다.

## 7. 로그 반영 및 합의 종료

유효한 Commit Certificate를 확보한 합의 인스턴스는 성공적으로 종료된다.

SM에는 동일한 논리적 요청이 한 번만 반영되어야 한다.

동일한 논리적 요청에 대해 여러 CC가 생성되더라도, 동일한 작업의 중복 반영은 허용하지 않는다.

합의가 성공하면 최종 CC를 클라이언트에게 반환한다.

합의가 실패하면 실패 결과를 반환한다.

## 8. Byzantine 공격 시나리오

### 8.1. 비잔틴 클라이언트

#### Replay

동일한 논리적 요청을 동일한 `requestId`로 재전송하면 동일한 요청 식별이 가능하다.

여러 CC가 생성되더라도 SM은 해당 작업을 한 번만 반영한다.

#### 거짓 요청

클라이언트가 자신의 개인키로 거짓 요청에 서명하는 행위는 가능하다.

다만 Merge의 Valid 검증에서 구현체별 업무 규칙과 요청 유효성 조건을 검사할 수 있다.

서명은 클라이언트 인증 및 요청 무결성을 보장할 뿐, 요청 내용의 진실성 자체를 보장하지 않는다.

#### Equivocation

동일한 `proposeId`에 서로 다른 요청 내용을 연결하는 행위는 해시 충돌 저항성에 의해 배제된다.

서로 다른 `proposeId`를 사용하는 요청은 서로 다른 합의 인스턴스로 취급한다.

#### Concurrent Request

동일한 요청의 동시 제출은 동일한 논리적 작업으로 취급할 수 있다.

서로 다른 `requestId`를 사용하는 동일한 요청 내용은 별개의 작업으로 취급한다.

서로 다른 요청 내용은 별개의 합의 인스턴스다.

### 8.2. 비잔틴 노드

#### Silent

**Propose 전체 침묵**

합의 시작 전 클라이언트가 어떠한 정직 노드에게도 요청을 전달하지 못한 경우는 프로토콜의 보장 범위 밖이다.

**Propose 일부 침묵**

정직 노드 하나 이상이 요청을 수신했다면 Prepare에서 다른 정직 노드에게 전파할 수 있다.

**Prepare 침묵 및 일부 침묵**

정직 노드의 요청 전파가 이루어지므로 비잔틴 노드의 침묵만으로 정직 노드 간 요청 전달을 차단할 수 없다.

**Merge 침묵 및 일부 침묵**

최대 $f$개의 노드가 침묵하더라도 정직 노드는 최소 $f+1$개 존재한다.

따라서 정직 노드들이 유효한 요청에 대해 응답한다면 $f+1$개의 서명을 확보할 수 있다.

**Commit 침묵 및 일부 침묵**

정직 노드가 유효한 CC를 확보하면 이를 다른 노드에게 전파한다.

따라서 비잔틴 노드의 선택적 침묵만으로 유효한 CC의 전파를 차단할 수 없도록 한다.

#### Equivocation

**Propose Equivocation**

동일한 `proposeId`에 서로 다른 요청 내용을 연결하려는 행위는 해시 검증에서 거부된다.

**Prepare Equivocation**

동일한 합의 ID에 상충하는 요청 내용을 전달하려는 행위는 해시 검증에서 거부된다.

**Merge Equivocation**

비잔틴 노드가 서로 다른 주장이나 응답을 전달하더라도, 정직 노드는 유효한 서명이 포함된 응답만 인정한다.

비잔틴 노드의 서명은 정직 노드의 서명을 대신할 수 없다.

**Commit Equivocation**

Commit Certificate는 동일한 `proposeId`와 세부 데이터를 대상으로 하는 $f+1$개의 유효한 서명을 요구한다.

비잔틴 노드는 다른 노드의 서명 없이 유효한 CC를 위조할 수 없다.

## 9. 보장하려는 안전성 및 활성성

New MBQ는 다음 속성을 목표로 한다.

### Agreement

동일한 합의 인스턴스에 대해 정직 노드들이 상충하는 요청을 커밋하지 않는다.

### Validity

유효하지 않은 요청에 대해 정직 노드가 Commit 서명을 제공하지 않는다.

### Termination

합의 시작 조건과 동기 통신 가정이 충족되고 유효한 요청이 전달되면, 정직 노드들은 고정된 4개 페이즈 내에서 합의를 종료한다.

### Certificate Uniqueness

하나의 합의 인스턴스에 대해 로그에 저장되고 반영되는 최종 합의 결과는 하나여야 한다.

### Idempotent Application

동일한 논리적 요청에 대한 중복 커밋 인증서가 생성되더라도 SM에는 해당 작업이 한 번만 반영된다.

## 10. 프로토콜 요약

$$
\boxed{
\text{Propose}
\rightarrow
\text{Prepare}
\rightarrow
\text{Merge}
\rightarrow
\text{Commit}
}
$$

| Phase | 핵심 역할 |
|---|---|
| Propose | 클라이언트 요청 제출 및 합의 시작 |
| Prepare | 정직 노드 간 요청 전파 |
| Merge | 유효성 검증 및 Commit 서명 수집 |
| Commit | CC 검증, 전파 및 로그 반영 |

**핵심 설계 원칙:** 요청 전파와 서명 수집을 분리하고, $f+1$개의 유효한 노드 서명을 통해 커밋 인증서를 구성하며, 최종 반영은 Commit 페이즈에서만 수행한다.
