# Salix Consensus - Leaderless Byzantine Consensus with Majority Quorums and Constant Phases

[//]: # (명세 v3 &#40;순서 보존 제외)

## 1. 개요

Salix는 동기 통신과 암호학적 디지털 서명을 이용하여, 전체 노드 중 과반 미만의 비잔틴 노드와 비잔틴 클라이언트가 존재하는 환경에서 **요청 단위 합의**(서명된 요청에 대한 Commit Certificate 기반 일치)를 수행하는 Byzantine Consensus Protocol이다.

전체 노드 수를 $n=2f+1$로 정의하며, 최대 $f$개의 비잔틴 노드를 허용한다.

프로토콜은 세 개의 고정 페이즈와, 페이즈에 묶이지 않는 상시 Commit 절차로 구성된다.

$$
\boxed{
\text{Propose}
\rightarrow
\text{Prepare}
\rightarrow
\text{Merge}
}
\quad+\quad
\boxed{\text{Commit (타이밍 무관, 상시 전파 절차)}}
$$

Salix의 주요 특징은 다음과 같다.

- 리더(제안자)가 없다.
- $n=2f+1$ 환경에서 $f+1$개의 노드 서명으로 Commit Certificate(CC)를 구성한다.
- 요청 전파(Prepare)와 서명 수집(Merge)을 분리한다.
- Commit은 페이즈가 아니라 타이밍과 무관한 상시 절차이며, 유효한 CC를 받은 노드는 무조건 한 번 전파한다.
- 정직 노드가 요청을 제때 받으면, 비잔틴 노드의 협조 없이 Merge 종료 시점에 모든 정직 노드가 CC를 보유한다.
- 이 버전은 **요청 간 순서를 보장하지 않는다** (12장).
- 별도의 Fail Recovery는 지원하지 않는다.

## 2. 시스템 모델 및 가정

### 2.1. 노드 구성

전체 노드 수는 다음과 같다.

$$
n=2f+1
$$

- 정직한 노드: 최소 $f+1$개. 정직한 노드는 장애가 없으며 프로토콜을 따른다.
- 비잔틴 노드: 최대 $f$개.

비잔틴 노드는 다음 행위를 할 수 있다.

- Equivocation
- Silent 및 Partial Silent
- Collusion
- Crash
- 임의의 잘못된 메시지 전송

### 2.2. 클라이언트

클라이언트 역시 비잔틴일 수 있다.

비잔틴 클라이언트는 다음 행위를 할 수 있다.

- 사칭 시도
- 거짓 요청
- Replay
- Concurrent Request
- 임의의 요청 식별자 생성

클라이언트의 신원과 요청 인증은 암호학적 서명을 통해 검증한다.

정직한 클라이언트는 요청을 **$f+1$개 이상의 노드**에게 전송한다 (정직 노드가 최소 하나 포함되도록 하기 위함).

### 2.3. 암호학적 가정

1. 노드와 클라이언트는 서로의 공개키를 알고 있으며 서명을 검증할 수 있다.
2. 디지털 서명은 위조할 수 없다.
3. 해시 함수는 충돌 저항성을 만족한다.
4. 정직한 노드는 자신이 생성한 서명을 임의로 위조하거나 변조하지 않는다.
5. 서명은 메시지 종류와 대상을 포함하여 도메인이 분리된다 (요청 서명과 Commit 서명은 서로 대체될 수 없다).

### 2.4. 네트워크와 시간

네트워크는 동기식이다.

- $\Delta$: 정직한 노드 간 메시지 전달 지연의 상한
- $B_k$: 페이즈 $k$ 시작 시점의 정직 노드 간 진입 편차 상한
- $\epsilon$: 서명 검증과 스케줄링에 걸리는 처리 시간의 상한

정직한 노드가 전송한 메시지는 $\Delta$ 안에 다른 정직한 노드에게 전달된다.

### 2.5. Fail Recovery와 결과 미정

Salix는 프로토콜 자체의 Fail Recovery를 지원하지 않는다. 합의 도중 발생한 노드 장애에 대한 복구 및 재개는 구현체에서 처리한다.

**"실패"는 확정된 결과가 아니라 "결과 미정"이다.** 노드가 어떤 시점까지 CC를 받지 못했다는 사실은 그 이후에도 CC가 존재하지 않는다는 뜻이 아니다 (비잔틴 노드가 CC를 숨겼다가 공개할 수 있다).

## 3. 요청 및 합의 식별

### 3.1. 요청 구성

클라이언트는 합의 요청을 생성할 때 다음 정보를 제공한다.

```text
Request {
    requestId
    clientRequest
    clientSignature
}

clientSignature = Sign(clientSK, "REQ" ‖ requestId ‖ clientRequest)
```

`proposeId`는 클라이언트가 제공하는 값이 아니라 **노드가 계산하는 파생 값**이다 (`proposeId`는 `clientSignature`를 입력으로 하므로 서명이 `proposeId`를 포함할 수 없다).

### 3.2. Propose ID

합의 인스턴스의 식별자인 `proposeId`는 다음과 같이 정의한다.

$$
proposeId =
H(
clientSignature
\parallel
clientRequest
\parallel
requestId
)
$$

서로 다른 요청 내용이 동일한 `proposeId`를 갖는 상황은 해시 충돌 저항성에 의해 배제한다. 따라서 하나의 합의 인스턴스 ID에 서로 다른 요청 내용을 연결할 수 없다.

서명 방식이 비결정적이면 동일한 논리적 요청이 서로 다른 `proposeId`를 가질 수 있다. 이 경우 서로 다른 인스턴스로 취급하되, SM에서 3.3의 기준으로 중복을 제거한다.

### 3.3. Request ID

`requestId`는 요청의 고유성과 멱등성을 관리하는 식별자다.

주요 규칙은 다음과 같다.

- 동일한 논리적 요청을 재전송하는 경우 동일한 `requestId`를 사용한다.
- 동일한 요청 내용이라도 새로운 작업이라면 새로운 `requestId`를 사용할 수 있다.
- 요청 내용이 다르면 동일한 `requestId`를 사용하더라도 별개의 요청으로 취급한다.
- `requestId`는 반드시 순차적이거나 전역적으로 유일할 필요가 없다.

예시:

| 요청       | Request ID | 처리               |
|------------|-----------:|--------------------|
| PUT x = 10 |          1 | 신규 작업          |
| PUT x = 20 |          2 | 신규 작업          |
| PUT x = 10 |          3 | 별개의 신규 작업   |
| PUT x = 10 |          1 | 기존 작업의 재전송 |

동일한 논리적 요청이 여러 번 커밋되더라도 SM에는 한 번만 반영되어야 한다.

중복 반영 여부는 클라이언트의 신원, `requestId`, 요청 내용을 기준으로 판단한다.

## 4. Commit Certificate

Commit Certificate(CC)는 특정 합의 인스턴스에 대한 요청 전체와 노드들의 Commit 서명 집합이다.

```text
CC {
    request: { requestId, clientRequest, clientSignature }
    sigs:    { (nodeId, commitSignature) }
    order:   ⊥        // 예약 필드. 현재 미사용 (12장)
}

commitSignature = Sign(nodeSK, "COMMIT" ‖ proposeId ‖ H(request) ‖ order)
```

CC 하나에서 `proposeId`, 요청, 서명자를 모두 추출할 수 있다.

유효한 CC는 다음 조건을 만족해야 한다.

1. 서로 다른 노드의 서명을 최소 $f+1$개 포함한다.
2. 모든 서명은 유효해야 한다.
3. 모든 서명은 동일한 `proposeId`와 동일한 요청 데이터(`H(request)`)에 대응해야 한다.
4. `proposeId`가 `request`로부터 재계산한 값과 일치한다.
5. 클라이언트 서명이 유효하고 요청 형식이 유효하다.
6. 구현체의 **상태 무관** 유효성 규칙을 통과한다.

$$
|CC|\geq f+1
$$

서명 자체가 서로 다르더라도, 동일한 `proposeId`와 동일한 요청 데이터를 대상으로 하는 $f+1$개 이상의 유효한 서명 집합은 동일한 합의 결과에 대한 CC로 취급한다.

하나의 합의 인스턴스에서 생성된 CC는 해당 인스턴스에만 유효하다.

## 5. 프로토콜

### 5.1. Propose

**목적: 합의의 시작.**

클라이언트는 자신이 생성한 요청을 노드에게 전달한다.

```text
Propose(
    requestId,
    clientRequest,
    clientSignature
) -> ()
```

노드는 Propose 구간에 요청을 수신하면 `proposeId`를 계산하고 클라이언트 서명과 형식, 상태 무관 규칙을 검증한다. 검증을 통과한 요청만 Prepare에서 전파한다.

Propose는 합의 시작을 알리는 단계이며, 이 단계에서 Commit 서명을 수집하지 않는다.

### 5.2. Prepare

**목적: 요청의 전파.**

```text
Prepare(
    requestId,
    clientRequest,
    clientSignature
) -> ()
```

노드는 **Propose 구간에 직접 수신하여 검증을 통과한 요청**을 다른 모든 노드에게 전파한다.

**Prepare로 수신한 요청은 다시 전파하지 않는다.**

Prepare의 주요 목적은 비잔틴 노드나 클라이언트가 요청을 일부 노드에게만 전달하는 상황을 보완하는 것이다. 동기 네트워크 가정 아래, 정직 노드 하나가 요청을 Propose 구간에 수신하고 전파하면 모든 정직 노드가 Prepare 구간 안에 해당 요청을 수신한다.

Prepare는 투표나 커밋 결정 단계가 아니다.

### 5.3. Merge

**목적: 요청 유효성 검증 및 Commit 서명 수집.**

요청 본문을 보유한 노드는 다른 노드들에게 해당 합의 인스턴스에 대한 서명을 요청한다.

```text
MergeRequest(proposeId) -> (isValid, commitSignature)
```

요청을 받은 노드는 다음을 검증한다.

- `proposeId`의 해시 검증
- 클라이언트 서명 검증
- 요청의 형식 검증
- 구현체의 **상태 무관** 유효성 규칙

**상태 의존 검증(잔고, 이미 처리된 요청 여부 등)은 Merge에서 하지 않는다.** 노드마다 SM 상태가 달라 정직 노드가 서로 다른 `isValid`를 낼 수 있기 때문이다. 상태 의존 검증은 적용 단계(7장)에서 결정적으로 수행한다.

요청 본문을 보유하지 않은 노드는 `isValid = 0`으로 응답하고 서명을 제공하지 않는다. 검증을 통과하면 `isValid = 1`과 함께 Commit 서명을 응답한다. 자신의 서명은 자신의 수집분에 포함한다.

서로 다른 노드의 유효한 Commit 서명을 $f+1$개 모으면 CC를 구성하고 `Commit(cc)`를 호출한다 (5.4).

구현체별 추가 규칙은 동일한 입력에 대해 모든 정직 노드가 동일한 결과를 내는 **상태 무관 규칙**이어야 한다.

### 5.4. Commit

**목적: CC의 검증, 전파, 반영. 페이즈가 아니라 상시 절차다.**

```text
Commit(cc) -> ()
```

입력은 CC 하나이며 필요한 모든 정보는 CC에서 추출한다. Merge에서 CC를 구성한 노드도 자신에게 `Commit(cc)`를 호출하여 같은 경로를 탄다. 타이밍 제약은 없으며, 페이즈 종료 이후에 도착한 CC도 처리한다.

```text
on Commit(cc):
    id = cc.proposeId
    if broadcasted[id]: return              // 이미 전파한 인스턴스는 검증 없이 종료
    if !verify(cc): return                  // 4장의 유효 조건 전부
    atomically:                             // 동시 수신 경쟁 방지
        if broadcasted[id]: return
        broadcasted[id] = true
    broadcast(cc, everyone)                 // 전파가 SM 실행보다 먼저
    if !applied[id]:
        applied[id] = true
        result = apply(cc)                  // 7장
    reply(client, id, result)
```

규칙은 다음과 같다.

- `broadcasted[id]`는 **검증을 통과한 뒤에만** 기록한다 (가짜 CC가 `proposeId`를 선점하지 못하게 한다).
- 중복 판단은 CC 바이트가 아니라 `proposeId`로 한다 (서명자 조합이 다른 유효 CC를 반복 전파시키는 증폭을 막는다).
- 전파는 SM 적용과 독립적이다. 적용이 지연되거나 실패해도 전파는 수행된다.
- 서로 다른 `proposeId`가 같은 논리적 요청을 나타내는 경우의 중복 제거는 SM이 담당한다.

## 6. Phase Stability

각 노드는 현재 페이즈에서 자신을 포함한 서로 다른 $f+1$개 노드의 유효한 응답을 확보하면 대기 타이머 $s_k$를 시작한다.

타이머가 만료되면 해당 페이즈를 종료하고 다음 페이즈로 전환한다.

### 6.1. 페이즈 전환 투표

- 자신의 현재 페이즈 연산이 완료되면 자기 자신을 페이즈 전환 투표에 포함한다.
- 서로 다른 노드의 유효한 응답만 투표수로 인정한다.
- 유효하지 않은 서명이 포함된 응답은 투표수에 포함하지 않는다.
- 자신을 포함한 $f+1$개 노드의 유효한 응답을 확보한 뒤 타이머를 시작한다.

Propose와 Prepare 페이즈에서 무엇을 "유효한 응답"으로 세는지는 11장의 열린 항목이다.

### 6.2. 타이머 조건

미래 페이즈 메시지의 처리 방식에 따라 다음 조건을 만족해야 한다.

| 페이즈                                | 조건                         | 비고                        |
|---------------------------------------|------------------------------|-----------------------------|
| Prepare (미래 페이즈 메시지를 버퍼링) | $s_k\ge\Delta+B_k$           | 단방향 전파                 |
| Prepare (`Try again` 후 재시도)       | $s_k\ge2\Delta+B_k+\epsilon$ | 왕복 포함                   |
| Merge                                 | $s_k\ge2\Delta+B_k+\epsilon$ | 요청-응답이므로 왕복이 필수 |

### 6.3. 페이즈 종료 이후의 요청

이미 종료된 페이즈에 도착한 메시지는 거부한다. 이는 이전 페이즈의 메시지를 이용한 지연 삽입 공격을 방지하기 위함이다.

**예외: CC(`Commit`) 메시지는 페이즈와 무관하게 처리한다.**

### 6.4. 미래 페이즈 요청

아직 시작하지 않은 미래 페이즈의 요청을 수신하면 다음 응답을 반환하거나 버퍼링한다.

```text
Try again
```

이 응답은 어떠한 합의 주장이나 투표도 의미하지 않는다. 발신자는 해당 요청을 재시도 대상으로 취급하며, 재시도에는 백오프와 횟수 상한을 적용한다.

## 7. 요청 적용과 클라이언트 응답

노드는 유효한 CC를 처음 받았을 때 `apply(cc)`를 수행한다.

- **상태 의존 검증**(잔고, 이미 처리된 요청 여부, 업무 규칙)은 이 단계에서 결정적으로 수행한다. 검증에 실패한 요청은 **SM 상태를 변경하지 않는 no-op**으로 처리하고, 클라이언트에게 그 결과를 반환한다.
- 동일한 논리적 요청에 대해 여러 CC가 생성되더라도 SM에는 한 번만 반영한다 (클라이언트 신원, `requestId`, 요청 내용 기준).

**클라이언트의 성공 판정.** 클라이언트는 CC 자체가 아니라, 서로 다른 노드 **$f+1$개**로부터 같은 `reply`를 받으면 성공으로 판정한다. 그 중 최소 한 노드는 정직하므로, 비잔틴 노드가 숨기고 있는 CC만으로는 성공이 성립하지 않는다.

CC를 받지 못한 클라이언트는 같은 `requestId`로 재시도한다.

## 8. Byzantine 공격 시나리오

### 8.1. 비잔틴 클라이언트

#### Replay

동일한 논리적 요청을 동일한 `requestId`로 재전송하면 동일한 요청 식별이 가능하다. 여러 CC가 생성되더라도 SM은 해당 작업을 한 번만 반영한다.

#### 거짓 요청

클라이언트가 자신의 개인키로 거짓 요청에 서명하는 행위는 가능하다. 서명은 클라이언트 인증 및 요청 무결성을 보장할 뿐, 요청 내용의 진실성은 보장하지 않는다. 업무 규칙 위반은 적용 단계에서 no-op으로 처리된다 (7장).

#### Equivocation

동일한 `proposeId`에 서로 다른 요청 내용을 연결하는 행위는 해시 충돌 저항성에 의해 배제된다. 서로 다른 `proposeId`를 사용하는 요청은 서로 다른 합의 인스턴스로 취급한다.

#### Concurrent Request

동일한 요청의 동시 제출은 동일한 논리적 작업으로 취급한다. 서로 다른 `requestId`를 사용하는 동일한 요청 내용은 별개의 작업이다. 서로 다른 요청 내용은 별개의 합의 인스턴스이며, **인스턴스 간 순서는 이 버전에서 보장하지 않는다** (12장).

#### 스팸

비잔틴 클라이언트가 유효하게 서명한 요청을 대량으로 생성하면 모든 정직 노드가 서명하고 전파한다. 요율 제한과 쿼터는 합의 계층 밖의 정책이다.

### 8.2. 비잔틴 노드

#### Silent

**Propose 전체 침묵.** 클라이언트가 어떠한 정직 노드에게도 요청을 전달하지 못한 경우는 보장 범위 밖이다. 정직 클라이언트는 $f+1$개 이상의 노드에게 전송하여 이를 피한다.

**Propose 일부 침묵.** 정직 노드 하나 이상이 Propose 구간에 요청을 수신했다면 Prepare에서 모든 정직 노드에게 전파된다.

**Prepare 침묵 및 일부 침묵.** 정직 노드의 요청 전파가 이루어지므로 비잔틴 노드의 침묵만으로 정직 노드 간 요청 전달을 차단할 수 없다.

**Merge 침묵 및 일부 침묵.** 최대 $f$개의 노드가 침묵하더라도 정직 노드는 최소 $f+1$개이므로, 요청을 가진 정직 노드들이 모두 서명하면 비잔틴 협조 없이 $f+1$개의 서명을 확보한다.

**Commit 침묵 및 일부 침묵.** 정직 노드가 유효한 CC를 받으면 즉시 전체에 전파하므로, 비잔틴 노드의 선택적 침묵으로 유효한 CC의 전파를 차단할 수 없다.

#### 일부 정직 노드와 담합한 부분 CC

비잔틴 노드가 요청을 Prepare 단계에서 일부 정직 노드에게만 보내 (Prepare 수신분은 재전파되지 않음), 일부 정직 서명과 비잔틴 서명으로 유효한 CC를 만들 수 있다. 이 CC는 유효한 요청에 대한 유효한 CC이므로 막지 않고 **무해하게 만든다.**

- 비잔틴이 CC를 정직 노드 한 명 이상에게 주면, 그 노드가 즉시 전파하므로 $\Delta$ 안에 모든 정직 노드가 같은 CC를 갖는다 (정리 T3).
- 정직 노드 누구에게도 주지 않으면 정직 노드는 커밋하지 않고, 클라이언트도 $f+1$개 노드의 응답이 없으므로 성공으로 판정하지 않는다 (7장).

#### Equivocation

**Propose / Prepare Equivocation.** 동일한 `proposeId`에 서로 다른 요청 내용을 연결하려는 행위는 해시 검증에서 거부된다.

**Merge Equivocation.** 비잔틴 노드가 서로 다른 응답을 전달하더라도, 정직 노드는 유효한 서명이 포함된 응답만 인정하며 비잔틴 노드의 서명은 정직 노드의 서명을 대신할 수 없다.

**Commit Equivocation.** CC는 동일한 `proposeId`와 요청 데이터를 대상으로 하는 $f+1$개의 유효한 서명을 요구한다. 비잔틴 노드는 최대 $f$개이므로 다른 노드의 서명 없이 유효한 CC를 만들 수 없다.

## 9. 보장하려는 속성

**Validity.** 유효한 CC는 클라이언트 서명, 형식, 상태 무관 규칙을 모두 통과한 요청에 대해서만 존재한다. 비잔틴 노드만으로는 어떤 요청에도 CC를 만들 수 없다.

**Uniqueness.** 하나의 `proposeId`에는 하나의 요청만 대응한다.

**Totality.** 어떤 정직 노드가 유효한 CC를 전파하면, 모든 정직 노드가 $\Delta+\epsilon$ 안에 같은 CC를 전파한다.

**Liveness.** 정직 노드 하나가 유효한 요청을 Propose 구간에 수신하면, Merge 종료 시 모든 정직 노드가 CC를 보유한다.

**Client Soundness.** 클라이언트가 성공으로 판정했다면(서로 다른 노드 $f+1$개의 같은 응답), 모든 정직 노드가 같은 CC를 보유하게 된다.

**Idempotent Application.** 동일한 논리적 요청에 대한 중복 CC가 생성되더라도 SM에는 한 번만 반영된다.

## 10. 정리와 증명

**T1 (Validity).** 유효한 CC의 요청은 클라이언트 서명, 형식, 상태 무관 규칙을 통과하고, 비잔틴 노드 단독으로는 CC를 만들 수 없다.

*증명.* 4장의 조건 5, 6은 `verify`가 강제한다. CC에는 서로 다른 노드의 서명이 $f+1$개 이상 있고 비잔틴 노드는 최대 $f$개이므로 정직 서명이 최소 하나 있다. 정직 노드는 검증을 통과한 요청에만 서명한다. $\square$

**T2 (Uniqueness).** 하나의 `proposeId`에는 하나의 요청만 대응한다.

*증명.* `proposeId`는 요청 내용과 클라이언트 서명의 해시이며, 충돌 저항성에 의해 다른 내용이 같은 값을 갖지 않는다. $\square$

**T3 (Totality).** 정직 노드 $i$가 시각 $t$에 `broadcast`를 수행하면 모든 정직 노드가 $t+\Delta+\epsilon$ 안에 `broadcast`를 수행한다.

*증명.* $i$가 전파한 CC는 유효하다. 각 정직 노드 $j$는 $\Delta$ 안에 이를 받는다. $j$가 이미 전파했다면 이미 수행한 것이고, 아니면 검증($\le\epsilon$) 후 전파한다. 5.4의 절차는 페이즈와 무관하므로 경계 공격이 존재하지 않는다. $\square$

**T4 (Liveness).** 정직 노드 $h$가 유효한 요청 $R$을 자신의 Propose 구간에 수신하면, Merge가 끝날 때 모든 정직 노드가 $R$의 CC를 보유한다.

*증명.* $h$는 Prepare 시작 시점 $a_h$에 $R$을 전파한다. 정직 노드 $j$의 Prepare 진입 시점 $a_j$는 $|a_j-a_h|\le B_k$이고, 전파는 $a_h+\Delta\le a_j+B_k+\Delta\le a_j+s_k$ 안에 도착하므로 $j$의 Prepare 구간 안에 들어온다 (6.2의 조건). 따라서 Merge 시작 시 모든 정직 노드가 $R$을 가진다. $R$은 상태 무관 검증 결과가 모든 정직 노드에서 같으므로 모든 정직 노드가 서명한다. 각 정직 노드 $i$는 Merge 요청을 보내 모든 정직 노드로부터 $2\Delta+B_k$ 안에 응답을 받으므로 (6.2), 자신을 포함하여 정직 서명만으로 $f+1$개 이상을 모아 CC를 구성한다. 비잔틴의 협조는 필요하지 않다. $\square$

**T5 (Client Soundness).** 클라이언트가 서로 다른 노드 $f+1$개로부터 같은 `reply`를 받았다면, 모든 정직 노드가 $\Delta+\epsilon$ 안에 같은 CC를 전파한다.

*증명.* $f+1$개의 응답자 중 최소 하나는 정직하며, 정직 노드는 `broadcast` 이후에만 `reply`한다. T3에 의해 성립한다. $\square$

T1, T2는 동기성을 쓰지 않으므로 **비동기에서도 성립**한다. T3, T4, T5만 동기 가정($\Delta$, $B_k$)을 사용한다.

## 11. 한계와 열린 항목

**한계**

- **순서 없음.** 정직 노드가 CC를 받는 시점이 $\Delta$ 안에서 다르므로, 비가환 연산의 적용 순서는 보장하지 않는다. 이 버전의 보장은 "요청별로 모든 정직 노드가 같은 CC를 가진다"까지다.
- **상태 보관.** `broadcasted`, `applied`를 영구히 보관할 수 없다. 정리 기준(체크포인트 등)이 필요하며 정리 이후 도착하는 늦은 CC의 처리 규칙이 필요하다.
- **대역폭.** CC에 요청 전체를 담으므로 요청 크기 $\times O(n^2)$의 전송량이 든다.
- **동기 가정 위반.** $\Delta$ 또는 $B_k$가 깨지면 T3, T4, T5의 시간 상한이 보장되지 않는다. T1, T2는 유지된다.

**열린 항목**

1. Propose, Prepare 페이즈에서 "유효한 응답"의 정의 (6.1).
2. 진입 편차 $B_k$를 프로토콜이 어떻게 보장하는지의 증명 (현재는 가정).
3. 요율 제한 정책의 명세 위치.

## 12. 순서 보존 확장 (추후)

CC의 `order` 필드를 서명 대상에 포함하는 방식으로 확장할 예정이다. 이 필드만으로 순서가 보장되지는 않는다. 같은 위치에 서로 다른 요청의 CC가 모두 만들어질 수 있고($Q=f+1$은 정직 노드 교차를 보장하지 않음), 위치를 누가 정하느냐가 곧 합의 문제이므로, 확장 시 이 경합을 닫는 규칙이 필요하다.

## 13. 프로토콜 요약

$$
\boxed{
\text{Propose}
\rightarrow
\text{Prepare}
\rightarrow
\text{Merge}
}
\;+\;
\text{Commit(상시)}
$$

| 단계          | 핵심 역할                                     |
|---------------|-----------------------------------------------|
| Propose       | 클라이언트 요청 제출                          |
| Prepare       | Propose 수신분의 전파 (재전파 없음)           |
| Merge         | 상태 무관 검증과 Commit 서명 수집, CC 구성    |
| Commit (상시) | CC 검증, 한 번 전파, SM 적용, 클라이언트 응답 |

**핵심 설계 원칙:** 요청 전파와 서명 수집을 분리하고, $f+1$개의 유효한 노드 서명으로 CC를 구성하며, CC는 타이밍과 무관하게 받으면 한 번 전파하여 정직 노드 사이의 일치를 확보한다.
